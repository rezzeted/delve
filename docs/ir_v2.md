# Delve IR v2/v3 (F4/F5)

Формат артефакта — `delve-ir/3` (поправка D3: позиционно-независимые id
стен/узлов — владелец + позиция в контуре владельца, без мировых координат;
кэш F8 переживает перераскладку. Читатель принимает и `delve-ir/2` — id для
него непрозрачны). Текст ниже описывает ядро; где v2 и v3 расходятся, это
отмечено явно.

Два входа в одно ядро (`src/libs/delve/ir.cpp`, `build_core`):

- **Frozen-путь (D0/D1)** — `build_ir_v2`: замороженный IR `delve-ir/0` + проект
  наполнения (любой, включая v1). Источник истины — `grid` замороженного IR;
  хранящийся там `contour` в метрах игнорируется (смена `cell`/`wall_t` — без
  edgar, тест `IrCorner.RetuneWithoutEdgar`). Ограничения входа: только
  прямоугольники, только двери в 1 клетку, `dtype` всегда `open`, роли по
  флагу corridor (v0-маппинг), толщина проектная единая.
- **Layout-путь (D2.3b)** — `build_ir_from_layout`: `delve-layout/0` + проект
  `delve-project/1`. id и роли — из графа; `dtype` — из ребра графа по паре
  комнат (project_v1); двери любой длины; фигурные ортогональные контуры;
  значения наполнения — по полной иерархии 4.2 (`resolve_room_fill`: комната →
  шаблон → роль → проект), включая `wall_t` на комнату.

Раскладка не обязана быть свежей: layout/0 читается из файла, edgar не нужен.
Несоответствие раскладки графу (лишняя/отсутствующая комната, другая роль или
флаг corridor, дверь без passage, непарная дверь, самопересекающийся контур) —
ошибка построения с именами.

## Стены (§5.2)

- Атомизация: каждое ребро контура делится во всех вершинах, лежащих на его
  линии (T-правило 5.2), двери атомы НЕ делят (дверь — вырез, не стык).
  Сторона комнаты на атоме — по направлению обхода (CW-контур: внутренняя
  сторона справа), поэтому фигурные контуры работают без изменений (поправка
  D2.3b; на прямоугольниках совпадает с прежним bbox-правилом — закреплено
  побайтовым сравнением путей в `IrFromLayout.MatchesFrozenPath`).
- Атом = один юнит тела. Общий атом — одно тело, владелец = min id комнат;
  наружный — своей комнате. Толщина — `wall_t` владельца (4.2; поправка D2.3b:
  была проектной единой). Если стороны общего атома разрешили разную толщину —
  ошибка F4 с именами обеих комнат, строить дальше нельзя (§5.2 дословно).
  Узел берёт толщину владельца без проверки соседей — точечные контакты стен
  разной толщины в узлах допустимы рабочим правилом 5.2.
- id: `wall:<owner_room>:<edge>[.<k>]` (поправка D3: было
  `wall:<x0>,<y0>-<x1>,<y1>` по координатам сетки — перераскладка ломала id и
  сиды юнитов). `edge`/`k` — ребро и порядковый атом по атомизированному
  контуру владельца (как у `fac:`; `.k` — только при >1 атоме на ребре).
- Комнаты атома — слева/справа от оси `g0 → g1`; высоты обеих сторон хранятся
  (`h` в JSON; у наружной вторая = высота владельца).
- Тело идёт между гранями столбов: отступы на концах — половины толщин УЗЛОВ
  на концах атома (`thick_ends`; поправка D2.3b — точно и при смешанных
  толщинах). Поле аддитивное: файлы без него читаются как «оба конца = thick».

## Узлы (§5.2)

- Узел — в каждой вершине, где сходятся ≥2 стен (все углы + все T-вершины),
  ровно один на координату. Владелец = min id смежных комнат.
- id: `node:<owner_room>:<v>` (поправка D3: было `node:<gx>,<gy>`); `v` —
  индекс вершины в атомизированном контуре владельца (углы и T-вершины по
  обходу от вершины 0).
- Грань закрыта, если из вершины вдоль её нормали уходит стена; иначе открыта.
- Комната за открытой гранью — пробник на полклетки за плоскостью грани
  (point-in-polygon; поправка D2.3b: был bbox-тест по смежным комнатам — на
  валидных раскладках прямоугольников доказуемо то же самое, для фигурных
  комнат пробник точен). Нет комнаты — пустота (стиль владельца, экстерьер).
- Вогнутый угол (270°, левый поворот на CW-обходе): обе открытые грани смотрят
  в свою комнату (показано геометрически: квадрант выемки занят закрытыми
  направлениями). Их стили — стили флангов стыка (входная грань — стиль A,
  исходящая — стиль B).
- Переходов на вогнутых стыках в v1 НЕТ — доказуемо недостижимы: любая комната,
  делящая привершинный атом одного края выемки, делит и другой (её южная грань
  ложится на нижний край выемки), поэтому ключи side-правил обоих флангов
  совпадают и стили равны. Развёртка вогнутого стыка — как у обычного угла
  (зазор t без граней; «две грани по толщине» из 5.7 отложены до словаря
  правил, различающего фланги вогнутого стыка).
- Длина грани на развёртке: `thick`, если вершина строго внутри ребра комнаты
  (T-грань); иначе 0.

## Развёртки (§5.7)

- Одна развёртка на комнату: `s` в метрах вдоль обхода от вершины 0 (начало
  фиксировано контуром — id переходов не плавают при смене стилей).
- Облицовка занимает атом минус половины толщин столбов на концах (поправка
  D2.3b: были `thick/2` проектные); T-грань — `[s_v − thick/2, s_v + thick/2]`.
- Стиль облицовки — уровень «сторона» 4.2 поверх РАЗРЕШЁННОГО стиля комнаты
  (`apply_side_rules` от базы 4.2; поправка D2.3b: на layout-пути база —
  комната/шаблон/роль/проект, на frozen — роль/проект).
- **Сторона облицовки (поправка D2.3b, фикс):** сегмент лежит на грани тела со
  стороны СВОЕЙ комнаты (`+thick/2` к ней), нормаль `n` смотрит В комнату.
  До D2.3b было наоборот (облицовка садилась на дальнюю сторону стены);
  грани столбов были правильными всегда. Ловится новой проверкой
  `facing_bounds` (checks_v1) и пином знака в `IrCorner.RetuneWithoutEdgar`.
- id облицовок: `fac:<room>:<edge>[.<k>]` (суффикс `.k` — если ребро контура
  держит больше одного атома; поправка D1.1).

## Переходы (§5.7)

- Ровно один переход на стык с разными стилями флангов (угол или T-стык);
  T-грань при разных флангах получает стиль A (входящий по обходу).
- Стили: A = входящая облицовка, B = исходящая. id — порядок по (room, s).
- Положение: `corner` — `[s_j − w/2, s_j + w/2]`; `wall` — на стороне B от края
  стыка (`[s_B0, s_B0 + w]`; выбор стороны B зафиксирован в v1).
- Обрезка: зона пересекается с доступным (интервалы участников минус проёмы
  дверей); обрезка — `shortened` + предупреждение; пустая зона — вырожденная в
  точке стыка. Пересекающиеся зоны соседних переходов — предупреждение.
- Замыкание развёртки: стык «последняя → первая» разворачивается (`s1` может
  превысить периметр — честное развёрнутое значение). Ограничение v1: зоны
  шире удвоенного расстояния до начала обхода у НЕзамыкающих стыков режутся
  линейно (с предупреждением).
- Куски (`zones` облицовок/граней) самодостаточны: `t` меряется от
  НЕобрезанного `s0` (`t_at_l0 = l_origin − s0_orig`), `@width` — настроенная
  ширина; коды сторон A/B лежат на куске; `flip = 0` у облицовок, у T-граней
  0/1 (слоты §2.4; поправка D1.2).
- `seed` перехода — из id (`zone_seed`).

## Двери (§5.3–5.4)

- Вырезы тела/облицовок — ПОЛНЫЙ сегмент двери; чистый проём (минус `frame` с
  концов) — только юниту двери. `@h` вырезов = `door_h`.
- Длина — из сегмента (поправка D2.3b: frozen-путь по-прежнему принимает только
  1 клетку; layout-путь — любая ≥ 1; `clear = len × cell − 2 × frame`).
- Тип: frozen-путь — всегда `open` (в delve-ir/0 нет id сокетов; §9.1);
  layout-путь — тип из ребра графа (поправка D2.3b; `gate` доезжает до юнита —
  сквозной тест `DelveCheck.GenerateRectLevelEndToEnd`).
- F4-ошибки: `clear ≤ 0`; отступ от угла `< max(толщина стены, толщины столбов
  на концах)/2 + frame` (поправка D2.3b: был проектный `thick/2`); дверь не на
  общей стене своих комнат; дверь через T-стык (защита).
- Минимумы 5.4 (`min_passage`, `min_opening`) на F4 НЕ проверяются — это F11.

## Производное (§4.3)

- `corridor_clear[room]`: прямоугольник — min сторона × cell − `wall_t`;
  фигурный коридор (поправка D2.3b) — min по парам противоположных атомов
  комнаты (самая узкая часть рукава) − `wall_t`; консервативно на открытых
  выемках (U-образный коридор отмеряет и зазор выемки). Метрический контур
  комнаты = `grid × project.cell` (в IR не хранится — у F6 есть проект).

## Артефакт (F5)

- `delve-ir/3`: rooms / walls / facings / nodes / doors / transitions /
  warnings / derived. Порядок стабилен (по id; N6); запись→чтение→запись —
  побайтово (тест). Чужой `format` отклоняется с ожиданием и способом
  (перегенерировать из замороженного/проекта; N7); `delve-ir/2` читается (id
  непрозрачны, поведение идентично); для `delve-ir/1` подсказка напоминает
  про int id.

## Происхождение значений (F12, D3)

У комнат, облицовок, граней узлов, дверей и переходов — поле `prov`
(аддитивное, как `thick_ends`): цепочки разрешения по иерархии 4.2, чтобы на
запрос «откуда взялось это значение» IR отвечал сам, без проекта.

- `prov`: объект поле → массив шагов `{level, detail, value}` по возрастанию
  иерархии; последний шаг — победитель, шаги ниже — что он перекрывает.
- Уровни: `default` (хардкод-дефолты), `project` (fill.room_h при пустых
  roles, fill.wall_t, door_h/frame, transitions), `role` (detail — имя роли
  или `*`), `template` (detail — имя шаблона), `room` (detail — id), `side`
  (detail — `side_rules[i] (ключи)`; только сработавшие правила, в порядке
  применения), `passage` (dtype двери на layout-пути; frozen — `default`).
- Поля: комнаты — `h`, `style`, `floor`, `ceil`, `wall_t` (wall_t живёт в
  prov и в стенах/узлах; на frozen-пути цепочка wall_t — один шаг `project`,
  толщина проектная единая). Облицовки — `style` (цепочка комнаты + side-шаги).
  Грани узлов — `style` (копия смотренной комнаты / фланговой облицовки).
  Двери — `dtype`, `h`, `frame`, `thick` (цепочка wall_t владельца).
  Переходы — `pattern`, `width`, `place` (по одному шагу `project`).
- Явность полей ролей восстанавливается по `set_fields` записей (ключи,
  присутствовавшие в JSON записи роли; слоение над `*` явностью не считается).
  Программная правка загруженной записи цепочку не ломает (значение шага
  читается живым), но добавленное поле надо пометить в `set_fields`.
- Текстовый рендер цепочки — `format_prov` (победитель первым, затем
  перекрытое): `3.5 <- room "hall" <- role "hall" (3) <- default (3)`.
  Диагностика уже пользуется: ошибка 5.2 (разные толщины общей стены) печатает
  цепочки wall_t обеих сторон. Показ в превью/CLI — F9/F10.
- `/2`-файлы читаются с пустыми цепочками (тест `IrJson.ReadsV2WithoutProv`);
  круговорот запись→чтение→запись с prov побайтов (тест `IrJson.RoundTrip`).
  Пути frozen/layout различаются только уровнем `dtype` (по построению:
  у frozen нет passage) — тест `IrFromLayout.MatchesFrozenPath` нормализует
  ровно это место.
- `source`: frozen-путь — `{frozen, project}`; layout-путь — `{layout:
  {project, seed}, project}` (поправка D2.3b; аддитивно: читатель принимает
  оба; старые файлы с `frozen` читаются без изменений).
- id комнат — строки: десятичная форма id замороженного IR (`room:0`,
  `door:0-1`) на frozen-пути; id графа на layout-пути. Пустота в ссылках —
  `null`.
- Сиды: `unit_seed` = FNV-1a(`"<fill_seed>/<unit_id>"`) & 2³¹−1 (slots §1);
  `fill_seed` — сплит проекта v1 (project_v1 §Сиды; поправка D2.3b — раньше
  наполнение брало сырой seed проекта).

## Границы v2 (что НЕ делает F4)

- Frozen-путь: прямоугольники, двери 1 клетка, `open`, единая толщина, роли
  corridor/hall.
- Layout-путь: ортогональные простые полигоны (самопересечение — ошибка);
  зон на вогнутых стыках нет (недостижимы в v1, см. выше); линейная обрезка
  сверхшироких зон; правила сторон — только стиль (`side`/`adjacent_role`);
  наполнение комнаты (пол/потолок) v1-ассетом — только прямоугольники
  (ассетное ограничение, assets_v1).
